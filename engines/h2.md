# H2

> A small, fast, pure-Java relational database that runs embedded in the JVM (or as a single server) — ubiquitous for tests and desktop apps, but its clustering, durability, and isolation guarantees make it the wrong tool for production HA or critical data.

## Identity
- **Taxonomy / data model:** relational (SQL), single-node. Written in Java; runs embedded in-process via JDBC or as a TCP/PG-wire server.
- **Storage model:** row-store ([N-ary / record layout](https://dbdb.io/db/h2)). Default engine since 1.4.x is **MVStore**, a log-structured, copy-on-write, B-tree-of-pages key-value store (chunks appended then compacted) — closer to [lsm-vs-btree](../concepts/lsm-vs-btree.md) copy-on-write than classic in-place B-tree; legacy **PageStore** (in-place B-tree) still selectable. Optional LZF/DEFLATE page compression. Disk and in-memory databases supported.
- **Workload:** OLTP-flavored, but realistically an embedded/test/small-app store. Not OLAP, not HTAP. See [oltp-olap-htap](../concepts/oltp-olap-htap.md).

## Distribution & consistency
- **CAP under partition:** mostly **N/A — single-node**. H2's only multi-node story is a 2-node "[clustered" mode](http://www.h2database.com/html/advanced.html) (synchronous write to both copies) which is a primitive replication scheme, not a partition-tolerant distributed system; on node failure the cluster keeps running on the survivor and must be **manually re-clustered** after recovery. No automatic failover/consensus. See [cap-pacelc](../concepts/cap-pacelc.md), [replication-models](../concepts/replication-models.md).
- **PACELC:** N/A — single-node; no quorum or tunable latency/consistency knobs.
- **Default isolation & what's achievable:** default **READ_COMMITTED** under MVStore ([H2 docs](http://www.h2database.com/html/advanced.html#transaction_isolation)). The [`IsolationLevel` enum](https://www.h2database.com/javadoc/org/h2/engine/IsolationLevel.html) defines READ_UNCOMMITTED, READ_COMMITTED, REPEATABLE_READ, SNAPSHOT, and SERIALIZABLE (the latter three added to MVStore mode in 1.4.200; see [issue #174](https://github.com/h2database/h2database/issues/174)). **Crucially, H2's SERIALIZABLE is not true serializability**: it prevents all three read phenomena (dirty/non-repeatable/phantom reads) but [does not ensure equivalence of serial vs concurrent execution](http://www.h2database.com/html/advanced.html#transaction_isolation) — i.e. it does not prevent write-skew/serialization anomalies. MVStore uses row-level write locks + MVCC snapshots rather than table locks. See [isolation-levels](../concepts/isolation-levels.md), [mvcc](../concepts/mvcc.md). This is a case where "supports SERIALIZABLE" diverges from what you actually get.
- **Replication:** only the 2-node synchronous clustered mode above; single-leader/quorum models do not apply. No CDC-grade logical replication.
- **Tunable consistency?** No per-query consistency levels.
- **Clock dependency:** none for correctness. See [clocks-and-time](../concepts/clocks-and-time.md).

## Schema
- **Schema-on-write:** rigid relational schema, enforced at write time.
- **Migration / DDL:** standard `ALTER TABLE`; DDL is transactional in some paths but generally locks the affected table. No online-DDL story comparable to large RDBMSs; fine at H2's data sizes.
- **Type system:** rich SQL types including `ARRAY`, `JSON`, `UUID`, `GEOMETRY` (spatial, JTS-backed), `INTERVAL`, `ENUM`, large objects (BLOB/CLOB). No native vector/ANN type.

## Query interface
- **Language:** SQL, broadly SQL-standard, with **compatibility modes** that emulate Oracle, MySQL, PostgreSQL, MS SQL Server, DB2, Derby, HSQLDB, MariaDB syntax — a key reason it's used as a stand-in test DB.
- **Transactions:** full multi-statement ACID on a single node; **two-phase commit** supported. Savepoints supported.
- **Native vs app-side:** native joins, subqueries, aggregations, window functions, views; secondary indexes (B+tree on disk; hash/AVL in-memory); multi-dimensional spatial index; built-in fulltext search (native + Lucene-backed).
- **Stored procedures / UDFs:** user-defined functions and triggers written in **Java** (aliases to static Java methods); no PL/SQL-style procedural language of its own.

## Scaling & topology
- **Vertical only.** No sharding, no horizontal partitioning, no auto-rebalancing. Scale = bigger JVM/heap and disk.
- **Read replicas:** none beyond the 2-node clustered copy (which is a full synchronous replica, not a read-scaling tier).
- **Storage/compute separation:** none — embedded engine and data file are co-located. See [storage-compute-separation](../concepts/storage-compute-separation.md) (not applicable here).

## Performance & durability
- **Write path:** MVStore appends changes and uses a transaction log; on reopen after crash the log is replayed. **Crucially, durability is not guaranteed on power loss by default**: H2's own docs state it [does not guarantee that all committed transactions survive a power failure](http://www.h2database.com/html/advanced.html#durability_problems), and that in their testing "a bit more than one second of committed transactions may be lost" — because fsync timing is governed by `WRITE_DELAY` (default 500 ms) plus OS buffering, so the **data-loss window is roughly one-plus second of committed transactions** unless you set `WRITE_DELAY 0` / `CHECKPOINT SYNC` to force sync (at a large throughput cost). See [wal-and-durability](../concepts/wal-and-durability.md). This is the single most important caveat for anyone treating H2 as a system of record.
- **Throughput/latency:** very fast for small in-process workloads; in-memory mode is extremely fast. No meaningful published p99/tail characterization at scale because it is not a scale-out engine; tail latency is dominated by GC pauses (it lives in your JVM heap) and by MVStore compaction.
- **Compaction / GC:** MVStore reclaims space by rewriting live chunks (copy-on-write compaction); can run at close and incrementally. Being in-heap, JVM garbage collection directly affects pause behavior.

## Operations & maturity
- **Backup/restore:** `BACKUP`/`SCRIPT` commands, file copy of the `.mv.db` file (when closed/consistent). No built-in continuous PITR; recovery relies on transaction-log replay at open.
- **Observability:** `EXPLAIN`/`EXPLAIN ANALYZE` query plans; a built-in web console (H2 Console) for ad-hoc SQL; JMX optional. Limited compared to server-class RDBMSs.
- **Upgrade story:** in-process library upgrade = swap the JAR; note **on-disk file format changes across major versions** (e.g. 1.4 → 2.x) require export/import (`SCRIPT`) migration, not in-place. Day-2 burden is low precisely because it's small and single-node.
- **Maturity:** very mature (since 2004, author Thomas Mueller), enormously deployed via Spring Boot / test suites. **No Jepsen report exists** (single-node; not a distributed claim to test). Known failure modes: power-loss data loss with default WRITE_DELAY; corruption reports historically on abrupt kills; 2-node cluster requires manual re-sync.

## Ecosystem & people
- **Canonical use cases:** in-memory/embedded **test database** for JVM apps (drop-in for Postgres/MySQL via compat modes); desktop/embedded application storage; prototyping; small internal tools. Bundled as the default DB in many Java frameworks.
- **Anti-patterns:** primary production datastore for critical data, multi-writer/high-concurrency OLTP, anything needing HA/failover, large datasets, or true serializable transactions. Teams that ship H2 to prod "because tests passed on it" then hit Postgres/MySQL behavioral and durability differences.
- **Drivers / connectors:** native JDBC; speaks the PostgreSQL wire protocol (PG server mode) so some PG clients connect; integrates with Hibernate/JPA, Spring, Flyway/Liquibase. Not a CDC/Kafka/dbt/BI target in practice.
- **Community / support:** active OSS project, good docs, gentle learning curve; no large commercial vendor backing (community support).

## Licensing & cost
- **License:** dual-licensed **EPL 1.0 / MPL 2.0** — both permissive, file-level/weak copyleft; commercial-use friendly, no post-2018 source-available relicensing. See [license-taxonomy](../concepts/license-taxonomy.md).
- **Self-managed only:** no managed/SaaS offering; you embed the JAR or run the server yourself.
- **Lock-in:** minimal — standard SQL/JDBC; the main stickiness is its proprietary `.mv.db` file format and compat-mode quirks.
- **Cost model:** free; cost is just JVM memory/disk on your own host.

## Hardware / deployment
- **Resource profile:** memory-bound, in-JVM-heap; for in-memory mode the entire dataset must fit in RAM (heap), and even persistent mode is happiest when the working set fits in heap/page cache. CPU/GC sensitive.
- **Storage assumptions:** local file on the app host; no network-attached/distributed storage design. NVMe vs spinning matters only via fsync cost.
- **Footprint:** **embedded** (a single ~2 MB JAR, no separate process) or a single TCP server; also pure in-memory. Classic [embedded-databases](../concepts/embedded-databases.md) profile alongside SQLite/DuckDB/RocksDB.
- **Deployment:** in-process inside your application; container/k8s usage is just shipping the JAR or a small server container (not a clustered StatefulSet system).

## Bottom line
Reach for H2 when you want a zero-install, pure-Java SQL database **inside your JVM** — for tests, prototypes, desktop apps, or small embedded tools — especially using its compatibility modes to mimic your production RDBMS. Do **not** use it as the system of record for important data or any service needing HA, horizontal scale, or true serializability. The single biggest gotcha: by default it can **lose recently committed transactions on power loss** (the `WRITE_DELAY` window), and its two-node "cluster" is not a real fault-tolerant distributed database.
