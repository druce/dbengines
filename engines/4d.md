# 4D

> A 1980s-vintage all-in-one relational database + proprietary 4GL + IDE for building desktop/web/client-server business apps — you adopt the *platform*, not just the database, and it runs on a single server.

## When to use

**Use 4D if:**
- ✅ You're a small team building or maintaining a custom business app (CRM/ERP/inventory) and want one vendor stack covering DB + 4GL + IDE + web/REST server + reporting
- ✅ A single-server OLTP topology with modest concurrent user counts is sufficient
- ✅ You value a long, stable support history and integrated tooling over best-of-breed swappable components

**Avoid 4D if:**
- ❌ You need horizontal scaling — it's vertical-only single-server with no native sharding, and HA is just async log-shipping to a warm mirror
- ❌ You want standard SQL, mainstream ORMs, open-source freedom, or cloud-native elasticity (no official Linux server build)
- ❌ Your workload is analytics/OLAP-heavy or you're unwilling to commit to a proprietary 4GL with manual record locking and high lock-in

## Identity
- **Taxonomy / data model:** Relational (tables, fields, relations) tightly coupled with the 4D programming language and IDE, plus ORDA (Object Relational Data Access) for treating rows as objects. Not a multi-model store. ([dbdb.io](https://dbdb.io/db/4d), [4D ORDA docs](https://developer.4d.com/docs/ORDA/overview))
- **Storage model:** Row-store ("N-ary"), disk-oriented with an in-memory cache. A database is a set of files: structure file, data file, log/journal file, plus preferences and resources. Indexes are B+Tree, with inverted (keyword/full-text) and composite index types. See [lsm-vs-btree](../concepts/lsm-vs-btree.md). ([dbdb.io](https://dbdb.io/db/4d))
- **Workload:** OLTP — interactive business applications (CRM, ERP, inventory, vertical line-of-business apps). Not an analytics/OLAP engine; no columnar store or MPP. See [oltp-olap-htap](../concepts/oltp-olap-htap.md).

## Distribution & consistency
- **CAP under partition:** N/A — single-server architecture (shared-everything; one 4D Server process owns the data, clients connect remotely). Not a distributed/partition-tolerant system, so [cap-pacelc](../concepts/cap-pacelc.md) does not meaningfully apply.
- **PACELC:** N/A — single node.
- **Default isolation & what's achievable:** Read Committed. Transactions lock records they modify/create but not records merely read, so non-repeatable reads and phantoms are possible. ([dbdb.io](https://dbdb.io/db/4d)) See [isolation-levels](../concepts/isolation-levels.md). ⚠️ unverified — whether a stricter serializable mode exists is not documented; treat Read Committed with manual locking as the ceiling.
- **Replication:** No quorum/leader replication in the distributed-database sense. High availability is achieved via a **logical mirror**: the operational server segments its log file (`New log file`) and ships segments to a standby machine that replays them with `INTEGRATE LOG FILE` / `INTEGRATE MIRROR LOG FILE`. This is async log shipping to a warm standby, not synchronous replication. ([Setting up a logical mirror](https://doc.4d.com/4Dv20R2/4D/20-R2/Setting-up-a-logical-mirror.300-6078954.en.html), [INTEGRATE MIRROR LOG FILE](https://developer.4d.com/docs/commands/integrate-mirror-log-file)) See [replication-models](../concepts/replication-models.md).
- **Tunable consistency?** No per-query consistency levels. Concurrency is handled via **explicit, manual record locking** — the developer must lock/unlock records and avoid deadlocks; there is no automatic deadlock detection/prevention. ([dbdb.io](https://dbdb.io/db/4d))
- **Clock dependency:** None for correctness (single node). See [clocks-and-time](../concepts/clocks-and-time.md).

## Schema
- **Schema-on-write:** rigid relational schema defined in the structure file via the IDE's Structure editor.
- **Migration/evolution:** Schema changes are made in the structure editor; ORDA adds programmatic data-model access. ⚠️ unverified — locking behavior of structural changes (online vs. offline DDL) is not clearly documented; large structural changes on a live database should be treated as maintenance-window operations.
- **Type system:** standard SQL scalar types plus 4D-native types including Object (JSON-like), Collection (arrays), Picture/Blob, Date/Time. Full-text/keyword indexing for text search. As of **4D 21 LTS (Jan 2026)**, a native vector type with semantic/similarity queries was added to the language and ORDA, alongside an integrated AI engine. ([4D 21 LTS is Here](https://blog.4d.com/4d-21-lts-is-here/))

## Query interface
- **Language:** dual interface — the proprietary 4D programming language (a 4GL) for application logic and data access, plus an integrated **SQL engine** (added in v11, 2008) for SQL queries. ORDA provides an object-oriented query/ORM-style API over the relational model. ([Wikipedia](https://en.wikipedia.org/wiki/4th_Dimension_(software)), [dbdb.io](https://dbdb.io/db/4d)) ⚠️ unverified — exact SQL-standard compliance level; treat it as a useful subset rather than full SQL:2016.
- **Transactions:** multi-statement transactions with atomic commit/rollback; changes are buffered until commit so uncommitted data is not visible to others. ([dbdb.io](https://dbdb.io/db/4d))
- **Native vs app-side:** native B+Tree and composite/keyword indexes, relations (joins), and aggregations. Most non-trivial logic is written in the 4D language rather than pushed into SQL.
- **Stored procedures / UDFs:** yes — server-side stored procedures and methods written in the 4D language; ORDA exposes data-model class functions.

## Scaling & topology
- **Vertical vs horizontal:** **vertical only.** 4D Server is a single shared-everything process; you scale by giving it a bigger box. No native sharding, partitioning, or cluster of database nodes. ([dbdb.io](https://dbdb.io/db/4d))
- **Sharding:** none built in.
- **Read replicas:** the logical-mirror standby is primarily a DR/HA target, not a load-balanced read replica fleet; reads from it lag by the log-shipping interval (eventually consistent vs. the primary). ([Setting up a logical mirror](https://doc.4d.com/4Dv20R2/4D/20-R2/Setting-up-a-logical-mirror.300-6078954.en.html))
- **Storage/compute separation:** none — coupled storage and compute on one server. See [storage-compute-separation](../concepts/storage-compute-separation.md) (not applicable).

## Performance & durability
- **Write path:** a per-data-file log/journal (`.journal`) records every modification since the last backup, with the change, user, and timestamp — a WAL-style journal used for recovery and for feeding the logical mirror. See [wal-and-durability](../concepts/wal-and-durability.md). ([4D journaling overview via dbdb.io](https://dbdb.io/db/4d), [Backup and Restore](https://developer.4d.com/docs/Backup/overview)) ⚠️ unverified — exact fsync/group-commit policy and the precise crash data-loss window are not documented; recoverability depends on the journal being intact since the last backup.
- **Throughput/latency profile:** tuned for interactive desktop/client-server business workloads (modest concurrent user counts), not high-throughput OLTP benchmarks or analytical scans. ⚠️ unverified — no public p99/tail-latency figures.
- **Compaction / vacuum / GC:** B+Tree storage; periodic data-file compaction/maintenance is part of admin tooling. ⚠️ unverified — specifics of background GC and its p99 impact are not documented.

## Operations & maturity
- **Backup/restore, PITR:** built-in backup with an integrated backup manager; the journal enables roll-forward recovery from the last backup, and the logical mirror provides near-zero-data-loss DR. ([Backup and Restore](https://developer.4d.com/docs/Backup/overview), [Setting up a logical mirror](https://doc.4d.com/4Dv20R2/4D/20-R2/Setting-up-a-logical-mirror.300-6078954.en.html))
- **Observability:** IDE-based runtime explorer, debugger, and SQL query inspection; vendor admin tooling. ⚠️ unverified — no rich external metrics/slow-query-log story comparable to mainstream RDBMS.
- **Upgrade story:** version-pinned platform with LTS and feature-release (R) tracks. Current LTS is **4D 21 LTS** (released January 2026; 4D 21.1 LTS already shipped), succeeding the v20 LTS line. Upgrades are application-level (recompile/migrate against a new 4D version), typically with downtime; not a rolling cluster upgrade. ([4D 21 LTS is Here](https://blog.4d.com/4d-21-lts-is-here/), [4D 21.1 LTS released — Forum](https://discuss.4d.com/t/4d-21-1-lts-is-released/38404), [4D v20 LTS blog](https://blog.4d.com/4d-v20-lts-is-here/))
- **Maturity:** very mature — created 1984, shipping since 1987, cross-platform since 1995. Long production track record in vertical business apps. **No Jepsen report** (single-node engine — distributed consistency testing does not apply). ([Wikipedia](https://en.wikipedia.org/wiki/4th_Dimension_(software)))

## Ecosystem & people
- **Canonical use cases:** custom internal business applications (CRM/ERP/inventory, finance, healthcare, education, manufacturing) where one vendor stack covering DB + UI + language + deployment is attractive to a small team. **Anti-patterns:** internet-scale or horizontally-sharded workloads; heavy analytics/OLAP; polyglot ecosystems wanting standard SQL, mainstream ORMs, or best-of-breed swappable components; teams unwilling to commit to a proprietary 4GL and single vendor.
- **Drivers / ORMs / connectors:** primarily 4D's own stack (4D language, ORDA, built-in web/REST and WebSocket servers, 4D Write Pro). SQL access and ODBC connectivity exist for external integration; mainstream CDC/Kafka/dbt/BI connectors are not first-class. ⚠️ unverified — extent of third-party connector ecosystem.
- **Community / support:** niche but long-standing community (4D Forums), commercial support from 4D SAS and a network of integrators/consultancies. Docs are vendor-maintained and reasonably complete. Learning curve is dominated by the proprietary language and IDE rather than the SQL surface.

## Licensing & cost
- **License:** proprietary, closed-source commercial software from 4D SAS (France); not open source. No post-2018 relicensing event of note — it was never OSS. See [license-taxonomy](../concepts/license-taxonomy.md).
- **Self-managed vs managed-only:** self-managed (on-prem / your own server); deployment offerings have expanded toward web/cloud hosting, but the engine is not a managed cloud DBaaS in the RDS sense.
- **Lock-in:** high — the 4D language, ORDA, IDE, and proprietary file format bind the whole application to the platform; migrating off means rewriting application logic, not just exporting tables.
- **Cost model:** commercial per-developer / per-deployment / per-client licensing (4D Server + client/web user licensing). ⚠️ unverified — exact current price tiers; pricing is quote/subscription-based and not transparently published.

## Hardware / deployment
- **Resource profile:** memory-aided disk-oriented engine; benefits from RAM for its cache but does not require the full dataset in RAM. CPU/IO scaling is single-machine (vertical).
- **Storage assumptions:** local disk on the server; NVMe/SSD helps but no network-attached-storage-separation design. Working set need not fit in RAM.
- **Footprint:** single-node — standalone single-user mode or one 4D Server with remote clients. Not embedded-library, not clustered, not serverless.
- **Deployment:** on-prem Windows/macOS server only — there is **no official Linux server build**; Linux remains a long-standing unfulfilled community feature request, so deployment on Linux happens only inside Windows VMs/containers. Container/k8s deployment is not a native strength (single StatefulSet-style instance at most, no clustering). ([4D supported operating systems for v20](https://blog.4d.com/which-operating-systems-for-4d-v20/), [Linux version feature request — 4D Forum](https://discuss.4d.com/t/linux-version/23093))

## Bottom line
Reach for 4D if you are building or maintaining a custom business application as a small team and want a single integrated stack — database, 4GL, IDE, web/REST server, and reporting — from one vendor, on one server, with a long support history. Do **not** choose it for horizontally-scaled, analytics-heavy, high-concurrency, or polyglot-ecosystem systems, or if you need standard SQL, open-source freedom, or cloud-native elasticity. The single biggest gotcha: this is a proprietary *platform* with manual record locking and no horizontal scaling — adopting it is a long-term, high-lock-in commitment to the 4D language and a single-server topology, and HA depends on async log-shipping mirror setup rather than built-in clustering.
